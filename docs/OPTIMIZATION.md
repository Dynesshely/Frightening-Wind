# 优化方案：把 0.70 progress/tick 拉回模型上限

> 依据：`docs/MODEL.md` 的公式 + `modeling/` 的算例 + 182 tick 线上采样。
> 目标：把净升级速率从实测 0.70 拉到 6.0+ e/tick（模型给配置维度的上限是 12.4）。

## 诊断基线

| 指标 | 实测 | 目标 |
| --- | --- | --- |
| spawn + extension 存量 | 120 / 1300（9.2%） | 孵化前 ≥ 目标身体成本 |
| 容器存量 | 均值 75，10/13 次 < 100 | 稳定 200+ |
| 空手 creep | 53% | < 20% |
| 升级速率 | 0.698 progress/tick | ≥ 6.0 |
| 人口摊销 | 2.00 e/tick | ≤ 1.2 |

## 六项修复

### F1 造兵预算：从"瞬时可用能量"改为"目标身体成本"

**现状**：`mgr.spawn.js` 用 `room.energyAvailable` 当预算，实测均值 120，
`planBody` 只拼得出 1W1C1M（200 能量），5W1C1M（600）在结构上永远造不出来。

**改法**：
- `config.spawn.budget` 给每个角色一个"值得攒到"的身体预算；
- 能量不够目标成本就**不孵**（合法的投资等待），但设 `starveTicks` 兜底：
  等待超过该 tick 数就用当前能量造小一号，避免人口断档；
- 预算上限仍受 `energyCapacityAvailable` 约束。

**模型依据**：5W1C1M 造价 600、摊销 0.40 e/tick，产出 5 倍；
6 个 1W1C1M 造价 1200 才等价。单位劳动力成本差 2.6 倍。

### F2 运输阈值：hauler 不再"等一整车"

**现状**：`role.hauler` 阈值 100，容器均值 75 → 大部分时间在待命；
没货时还跑回老家（24 步），回来又 24 步，来回纯浪费。

**改法**：
- 阈值改为与自身运力挂钩：`max(30, carry * 0.4)`（2C1M → 40）；
- 没货时**守在最近的转运容器旁**等货，不再回老家。

### F3 优先级倒挂：upgrader 不再抢运输货源

**现状**：upgrader 阈值 50 < hauler 阈值 100，容器刚涨到 50 就被升级者抽走，
运输队永远等不到货。

**改法**：upgrader 取货顺序改为
1. `storage`（存量 > 300）；
2. 控制器 3 格内的容器；
3. 以上都没有 → 自己去采（不再动矿源旁容器）。

### F4 沉淀通道：能量要能"存住"

**现状**：`deliverEnergy` 只认 spawn/extension/tower，而这三者永远不满，
所有能量立刻被造兵花掉；`dumpSurplus` 依赖"控制器旁容器"，房间里没有。

**改法**：
- `deliverEnergy` 增加`storage`兜底：spawn/ext/tower 满了就往 storage 倒；
- `construction` 提升 storage 与"控制器旁容器"的规划优先级。

### F5 配额：按 WORK 数算，不按人头算

**现状**：`quota.miner` 按"地形站位"定编，每源最多 2 人，且假设
"2 个 3WORK 吃满 10 e/tick"——模型证伪：2 个 3WORK 只有 5.45 e/tick。

**改法**：按 `Y(n) = 10n/(5+n)` 反解所需 WORK 数：

    n = 5Y / (10 − Y)

| 目标 Y | 需要 WORK | 5W 矿工数 |
| --- | --- | --- |
| 5.0 | 5 | 1 |
| 6.67 | 10 | 2 |
| 8.0 | 20 | 4 |

RCL4 目标 6.67 → 每源 2 个 5W 矿工。

### F6 消耗端与供给匹配

**现状**：4 个 upgrader 的身体能吃 4 e/tick，实际供给 0.70，
83% 时间待命，而摊销 0.53 e/tick 占升级量的 76%。

**改法**：RCL4 先配 3 个，RCL5+ 再回 5 个；等 F1~F5 把供给拉起来后再加。

## 验收标准

| 阶段 | 指标 | 阈值 |
| --- | --- | --- |
| 回归 | `node all.js` | 全绿 |
| 线上 5 分钟 | 空手率 | < 40% |
| 线上 5 分钟 | 容器均值 | > 150 |
| 线上 10 分钟 | 升级速率 | > 2.0 |
| 线上 30 分钟 | 升级速率 | > 4.0 |

## 风险与回退

* F1 可能造成 spawn 长期空闲 → 用 `starveTicks` 兜底；
* F3 可能让 upgrader 供能不足 → 保留"自采"退路；
* 任一项导致回归失败，单独回退该文件。

## 实施结果（tick ≈ 396426）

### 总体

| 指标 | 优化前 | 现在 | 变化 |
| --- | --- | --- | --- |
| 升级速率 | 0.698 progress/tick | **1.632** | **+134%** |
| 到 RCL5 的墙钟时间 | 34.9 小时 | **14.4 小时** | −58% |
| spawn+扩展存量 | 均值 120 | 均值约 280（峰值 506） | +133% |
| 容器存量 | 均值 75 | 出现 698 的积压（产能信号） | — |
| 人口 | 17 → 崩到 6 | 稳定 14–17 | 恢复 |
| 空手率 | 53% | 约 45% | 略降 |
| 回归 | — | 全绿（语法 + 10 场景 + 边界 + 防御 20 + 规划 7） | — |

### 六项修复的落地情况

| 编号 | 改动 | 状态 |
| --- | --- | --- |
| F1 | 造兵预算改用目标身体成本 + tiers 档位 | ✅ 已生效（出现 2W2C2M / 3W1C2M / 6C3M） |
| F2 | hauler 阈值改为运力的 40%，没货守在容器旁 | ✅ 已生效 |
| F3 | upgrader 只从 storage / 控制器容器取货 | ✅ 已生效（不再抢矿） |
| F4 | 交付预算（spawn 囤够就转投控制器容器）+ storage 兜底 | ✅ 已生效 |
| F5 | 矿工配额按 WORK 缺口反解 | ✅ 已生效 |
| F6 | upgrader 4 → 3，与供给匹配 | ✅ 已生效 |

### 迭代中暴露的新问题（都已修掉）

1. **攒钱把人口攒没了**：只按预算等 600，850 tick 内人口从 17 掉到 6。
   → 加 `minPopulation` 保命模式（只补采集者）+ `starveTicks` 240→90。
2. **reserve 与 budget 互相锁死**：hauler 攒到 reserve 就停止喂 spawn，而孵化又要求 budget，
   两者相等时永远攒不到 → reserve 必须高于最高 budget。
3. **reserver 霸占孵化位**：它 650 能量的预算排在 spawnPriority 第一位，
   房间根本攒不到 → 改成经济角色优先。
4. **只数人头不数 WORK**：4 个 1W 矿工让配额判定为"已满"，5W 矿工永远轮不到
   → 配额改成按 WORK 缺口算。
5. **upgrader 跑去和矿工抢矿脉**：被 F3 断供后走"自采"分支，
   实测跑到 (43,28)/(43,29) 和矿工抢同一条矿 → 改成在控制器旁待命。
6. **塔抢走升级口粮**：塔有 340 能量仍被优先补满，控制器容器长期 0
   → 控制器容器提到塔之前，塔低于 500 才补。
7. **storage 是 30000 能量的黑洞**：3 个建造者灌进去后升级停摆
   → `canBuildStorage` 4→5，已在建的工地动态降级（能量不足 60% 时优先级 99）。

### 仍然存在的瓶颈（下一阶段）

1. **矿工 WORK 数**：房间里还有一批 1W1C1M 的老矿工，要等它们自然死亡（1500 tick）
   才轮到新孵的 3W 矿工补位。这是升级速率的主要剩余上限。
2. **source B 的容器经常为 0**：矿工补位速度还跟不上。
3. **storage 未建成**：能量沉淀只能靠控制器容器（容量 2000），
   RCL5 后再建 storage。
4. **空手率 45%**：仍有大量 creep 在跑空趟，下一轮要按"离目标距离"重排任务。

### 结论

从 0.698 到 1.632 是"把断掉的链路接上"的收益；再往上要靠**矿工换代**和
**运输调度**，属于下一阶段的工作。
